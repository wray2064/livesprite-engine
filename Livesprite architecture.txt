LiveSprite Engine definition

LiveSprite Engine is the deterministic math layer that stores, transforms, resolves, and compiles sprite instructions into pixels.

It does not know about:

animation timelines
source files
3D models
video
Practipuppets
Arranger layouts
engine importers
toolkit UI

It does know about:

regions
pixels-as-math
operations
palettes
fills
strokes
transforms
deforms
pivots
sockets
boundaries
raster resolution
deterministic compilation

The apps provide intent.
LiveSprite resolves the math.

inside the stroke geometry. Snap policy is what aligns a stroke to the grid, so

10. Transform operations

Transforms are central to LiveSprite.

Expose:

Translate
Rotate
Scale
Mirror
Shear
Skew
Squash
Stretch
MatrixTransform

Every transform should accept:

target
pivot
coordinate space
rounding policy
sampling policy
bounds policy

Targeting replaces the separate TransformRegion / TransformLayer / TransformSprite
entries: one operation carries targetRegion, targetLayer and target, and the
narrowest one set wins. A transform with a region applies to that region, else
to the layer, else to the sprite that owns the operation.

Two entries from the original list are deliberately absent.

PivotTransform is not an operation. It rotated and scaled about a pivot, which
is Rotate followed by Scale, both of which already take a pivot.

AnchorTransform is not an operation either. Attaching one sprite to another
sprite socket is not a per layer transform: it is a relationship between two
sprites, so it lives as attachment state (see section 12) and is set through
attachSprite. Keeping it as an operation as well meant two mechanisms could
place the same child in two different places.

Placing a whole sprite is also not an operation. A sprite carries its own
transform, set through setSpriteTransform or composed through translateSprite,
rotateSprite, scaleSprite and mirrorSprite. That transform is the single frame
that sockets, pivots and attached children all resolve through, so moving a
sprite moves everything hanging off it. Operations transform content inside a
sprite; the sprite transform places the sprite itself.

The core does not care if a transform came from a canvas gizmo, Animotron keyframe, Practipuppet, or importer.

It only resolves it.

12. Spatial anchors

These are core.

They are not animation features.
They are transform and composition metadata.

Pivot

Expose:

CreatePivot
SetPivot
GetPivot
MovePivot
FindPivot
PlacePivot
GetPivotWorldPosition
TransformAroundPivot

A pivot is named, so an app can find it without holding the id, and can be
placed from the compiled bounds (content centre, top, bottom, top left, or
canvas centre) so it follows the artwork instead of being retyped when the
drawing changes.

Meaning:

where rotation, scale, squash, and stretch originate
Socket

Expose:

AddSocket
RemoveSocket
MoveSocket
RotateSocket
SetSocketScale
FindSocket
GetSocketTransform
GetSocketWorldTransform
GetSocketWorldPosition
ResolveSocketAttachment

Meaning:

where another sprite’s pivot connects

A socket is a named frame on a sprite: position, orientation and scale. The
local transform is the frame as authored; the world transform is that frame
after the sprite own transform and every attachment above it, so a socket on a
turning arm turns with the arm.

Attachment

Expose:

AttachSprite
DetachSprite
GetAttachment
GetAttachedSprites
AssemblyOrder
CompileAssembly

Meaning:

a sprite hangs off at most one socket, presenting one of its own pivots

An attachment carries an optional joint offset and a flag for compositing under
the parent instead of over it. Chains resolve to any depth. Attaching rejects a
cycle rather than building one, and the pivot offered to a socket has to belong
to the child. AssemblyOrder walks the tree in compositing order; CompileAssembly
compiles each sprite from its own operations and places it by the chain.

Core knows attachment math.

The app decides whether the socket is a hand, weapon grip, backpack mount, or UI marker.

Boundaries

Expose:

CreateBoundary

Meaning:

where an operation has influence

Boundaries support:

Final core API shape

At the highest level, the engine exposes five categories:

1. Structure
   documents, sprites, layers, regions

2. Appearance
   fills, strokes, palettes, outlines, patterns

3. Motion math
   transforms, deforms, pivots, sockets, boundaries

4. Resolution
   sampling, rasterization, compilation, snapshots

5. Infrastructure
   dependencies, cache, serialization, extension hooks

The simplest definition:

LiveSprite Engine exposes the math required to define, transform, and resolve sprites. Everything that decides why, when, or from where those parameters come is app-side.

LiveSprite workflow philosophy

The central idea of LiveSprite-native apps is:

The artist manipulates sprites.
The engine manipulates mathematical intent.

The user never works directly on:

dead raster truth

even though the experience still feels like pixel art.

Two simultaneous workflows exist
1. Artist workflow

What the user experiences.

2. LiveSprite workflow

What the engine is actually doing internally.

These workflows intentionally do not look the same.

That separation is the entire design philosophy.

Example workflow:
drawing and animating a sword sprite

The artist experiences something familiar:

1. Draw sword
2. Fill blade
3. Add dithering
4. Rotate sword
5. Adjust outline
6. Duplicate frame
7. Stretch slash frame
8. Export sprite sheet

Feels like:

Aseprite

The “sprite” is really:
